## 1 三态口径（最终报告必须分三态，不得合并）

用户明确要求「最终分别报告代码完成、构建通过、模拟器验证通过三个状态」。三者是**递进但不等价**的关系，本项目已经踩过一次「构建成功＝功能通过」的误区（见 `evidence/运行验证报告-模拟器.md` §1）。

| 状态 | 含义 | 唯一有效证据 | 不得声称的情形 |
| --- | --- | --- | --- |
| **① 代码完成** | 文件已写、规格签名一致 | 文件清单 + `grep`/走查结论 + commit hash | 不得因为「写完了」就说功能可用 |
| **② 构建通过** | ArkTS 编译无错 | `scripts\build-hap.bat` 日志含 `Finished ::entry:default@CompileArkTS` + `BUILD SUCCESSFUL` + 零 `ArkTS:ERROR`，且记录 HAP 路径与字节数 | 不得因为构建通过就说运行正常；**本轮 `PreferencesStore`/`WriteQueue`/`Serializer` 在被 T4-03 引用前根本不进编译单元**，构建对它零证明力 |
| **③ 模拟器验证通过** | 在 API 17 模拟器上跑通本文 §4 的 12 步重启验收 | 截图 + `uilayout` 组件树 + `preferences` 落盘文件 + `hilog` 关键行 | 不得用 L2 断言、Previewer 或「代码走查」代替 |

**每一态都必须留下独立证据**，缺证据即视为该态未达成，报告里写「未达成」而不是留空。

## 5 降级（异常数据）验证方案 —— 含一处必须如实声明的边界

用户要求「检查异常数据降级处理」。**先说清能力边界，不许含糊过去**：

| 方案 | 可行性 | 说明 |
| --- | --- | --- |
| A. shell 手工改坏 `preferences` 里某个块 | ❌ **不可行** | `hdc shell` 为 `uid=2000(shell)`，对应用沙箱 `Permission denied`（已实测）。除非设备 root，否则做不了 |
| B. 在应用内造一个「写坏」调试入口 | ❌ **不做** | 属功能越界（阶段四「不做」清单），且会污染生产代码 |
| C. L2 注入损坏输入，证明解码层降级正确 | ✅ **采用（主证）** | 覆盖任务书 B4/B5/B9/B10/B11/B13 + C6 的解码侧 |
| D. 设备侧证明「存储全损仍能启动」 | ✅ **采用（辅证）** | `rm`/清空 `preferences` 后冷启动（若 shell 权限不允许，改用 `bm clean -d` 达成等价效果），验证不崩溃 + 回默认态 + 诊断可见 |

**因此 C6「手工把 KEY-08 某块写坏后重启」在真机上无法原样执行**，T4-05 必须写成：
> 「C6 已在 L2 以等价损坏输入验证（贴输出）；设备侧因 shell 无沙箱写权限无法原样复现，改用方案 D 验证『存储不可用时不崩溃并降级』。**未执行的部分如实标注，不计入通过。**」

**此外必须验证的两条降级语义**：
1. **单分区损坏不牵连全局**：某分区 `ok:false` → 该分区回退默认（日志型回退空数组），其余分区照常载入（不是整体重置）
2. **降级要可见**：`ResultCode.STORAGE_ERROR` + 设置页诊断区有记录（D6），且**不新造文案**（沿用 `messageOf(STORAGE_ERROR)`）
