## 3 门禁覆盖范围（本阶段最重要的过程事实）

### 3.1 事实：`CompileArkTS` 只检查「从入口可达」的模块

`hvigor` 的 ArkTS 编译任务以**应用入口**（`EntryAbility` / `@Entry` 页面）为根做可达性分析，
**只对可达闭包内的模块做类型检查**。未被任何入口引用的新文件，即使含明显类型错误，
构建依然通过。这**不是**猜测，是下面这次否证实验的结果。

**探针（已删除，未进任何提交）**：在 `entry/src/main/ets/service/` 下新建 `TypeCheckProbe.ets`：

```ts
export const PROBE_NUMBER: number = 'not-a-number';
```

该文件无任何 import、也未被任何文件引用。构建结果原文（`%TEMP%\probe-build.log`）：

```
> hvigor Finished :entry:default@CompileArkTS... after 14 s 481 ms
> hvigor BUILD SUCCESSFUL in 45 s 553 ms
```

**结论（否证成立）**：一个把 `string` 赋给 `number` 的错误文件，在不可达位置**不会**让构建失败。
因此「`BUILD SUCCESSFUL`」的正确含义是「**可达闭包内**类型正确 + 全工程语法可解析」，
**不等于**「整个 `ets/` 目录类型正确」。

**影响面（必须明说）**：T3-01 ~ T3-04 **新建了 15 个文件**（`Fifo` / `WriteGuard` / `RuleMatcher` /
`LogService` / `DeviceService` / `MockDeviceAdapter` / `EnvironmentService` / `EnvironmentSimulator` /
`RuleEngine` / `RuleService` / `RuleActionExecutor` / `SceneService` / `StatisticsService` /
`StatisticsContract` / `ExportService`），其中绝大部分在 T3-05 之前**未被页面引用**。
所以那几次 `BUILD SUCCESSFUL` 对这批新文件的类型正确性**只提供有限保证**——
它们证明了「能解析、能产出 HAP」，不能证明「类型检查通过」。

### 3.2 补救：临时类型枢纽（验证后已复原）

为在 T3-05 之前拿到真实类型检查结论，曾**临时**在 `EntryAbility.ets` 中加入一个
`TYPE_CHECK_HUB = false` 的私有方法 `typeCheckHub()`，把当批全部新类逐一引用进来
（`RuleEngine` / `RuleService` / `RuleActionExecutor` / `SceneService` / `StatisticsService` / `ExportService`），
使它们进入可达闭包，再做一次真实类型检查构建。

**这次枢纽构建第一次是失败的**，并因此改了一个设计形态。原文（`%TEMP%\t304-typecheck-hub.log`）：

```
> hvigor ERROR: Failed :entry:default@CompileArkTS...
1 ERROR: ArkTS:ERROR File: D:/SmartDormHarmonyOS/entry/src/main/ets/entryability/EntryAbility.ets:129:11
 Structural typing is not supported (arkts-no-structural-typing)
COMPILE RESULT:FAIL {ERROR:2 WARN:1}
```

根因：`StatisticsService` 当时只在注释里声明「实现 `IStatisticsService`」，未显式 `implements`。
ArkTS **不支持结构化类型**，接口赋值必须显式 `implements`；而把契约留在 `ServiceContracts.ets`
里做不到——该文件当时经 `MockDataFactory → common/IdGenerator → @kit.ArkTS` 命中系统 Kit，
而 `StatisticsService` 必须零 Kit 才能进 L2 单测。
**修复**：抽出零依赖的 `service/StatisticsContract.ets`（纯 interface，无 import），
`StatisticsService` 显式 `implements IStatisticsService`，`ServiceContracts.ets` 用
`export { IStatisticsService } from './StatisticsContract';` 保持既有 import 路径不变。

修复后枢纽构建通过（`%TEMP%\t304-hub2.log`）：

```
> hvigor Finished :entry:default@CompileArkTS... after 16 s 462 ms
> hvigor BUILD SUCCESSFUL in 46 s 758 ms
```

**验证完成后 `EntryAbility.ets` 用 `git checkout HEAD --` 复原，枢纽代码未纳入任何提交**
（`grep -rn "TYPE_CHECK_HUB\|typeCheckHub" entry/src/main/ets/` 命中为 0）。

### 3.3 限制的消失：T3-05 接线后，构建才是「全量类型检查」

T3-05 用 `ServiceFacade` 把 8 个服务 + 仓储全部接到页面可达路径上，`CompileArkTS` 从此
**常态覆盖**整个 service 层。可核查的证据：

1. **硬证据（可达性本身）**：`ServiceFacade.ets` 的 import 列表包含
   `DeviceService` / `EnvironmentService` / `RuleService` / `RuleEngine` / `SceneService` /
   `LogService` / `StatisticsService` / `ExportService`（8 个服务）与 `AppDataRepository`；
   而 11 个页面/组件 import 了 `ServiceFacade`（共 35 处引用，见 T3-05 汇报）→
   于是「入口 → 页面 → 门面 → 8 个服务」全部在可达闭包内。
2. **机制证据**：3.2 那次失败本身就是证明——只有当类**被枢纽引用进可达闭包**时，
   `arkts-no-structural-typing` 才会暴露；未引用时同样的代码构建通过（3.1）。
3. **旁证**：产物尺寸 1012641 → 1173058 的同向变化（仅旁证，不作唯一依据）。

### 3.4 由此确立的三条作业规则（阶段四继续执行）

1. **任何新文件在被入口引用之前，`BUILD SUCCESSFUL` 不能作为「类型正确」的证据**，只证明「语法能过、模块能被解析」。
2. 新增文件若暂不接入调用链，**必须**用临时类型枢纽验证后复原，并在汇报中贴枢纽构建原文行。
3. 每个任务收尾时，若能通过一条 grep 证明「新类已进入可达图」，优先做这条证明，而不是依赖构建行。
