## 3 本批新发现缺陷（未修源码，原样上报）

### P1 · Settings 两个总开关：显示与持久化态不一致，且提交时串改另一开关

- **复现**：① 关「环境模拟」→ 导出确认 `simulationEnabled=false`；② 重新进入「设置」页（或冷启动后首次进入）→ 页面仍显示「自动化：开 / 环境模拟：开」（局部 `@State` 初值硬编码为 `true`）；③ 点「自动化：开」→ 导出确认 `automationEnabled=false`（预期）**且 `simulationEnabled=true`（被悄悄改回开）**。
- **根因定位**：`entry/src/main/ets/pages/Settings.ets` 的 `refresh()` 只回填 `sampleInterval / logLimit / subscriberCount / dirtyCount / bootCount / lastLaunchAt / diagnostics`，**未回填 `automationOn` / `simulationOn`**；两者在 `@State` 声明处恒为 `true`，只有 `commitSettings()` 会赋值。因此 `commitSettings(!this.automationOn, this.simulationOn, …)` 会把陈旧的 `simulationOn=true` 一并写回。
- **影响**：TC-E-09 / TC-E-04 / TC-N-07 的开关准备阶段均需多次点击并逐次导出核对才能到达目标态；用户在实际使用中改一个开关会意外改另一个。
- **证据**：`evidence/device/st05c_e09_switch_check.json`、`st05c_e04_switch_check.json`、`st05c_e04_after_restart.json`、`screenshots/st05c_e04_automation_on.jpeg`、`screenshots/st05c_e09_automation_off.jpeg`。
- **建议**：`refresh()` 增加 `this.automationOn = settings.automationEnabled; this.simulationOn = settings.simulationEnabled;`。

### P1 · UI 删除设备触发 FR-02-05 悬空引用清理，与 TC-E-04 预期冲突

- **复现**：建规则指向灯 → DeviceList 删除该灯 → 导出 `rules[0]` 变为 `actions=[]`、`enabled=false`、`updatedAt` 更新。
- **说明**：这是实现侧主动清理（FR-02-05），可避免悬空下发，但与 PRD 第 16 章 TC-E-04「删掉目标设备后该规则仍产出 FAILED 日志」的预期不一致。本轮为验证引擎失败路径，改用 preferences 注入构造悬空规则（已如实标注），真实设备端确实产出 `FAILED / errorMsg=POWER_ON:NOT_FOUND` 且整轮不中断。
- **证据**：`evidence/device/st05c_e04_pretrigger.json`（清理后 `actions=[]`）、`st05c_e04_prefs_after.txt`（FAILED 日志）。
- **建议**：主理人裁决「清理行为为正确实现、用例预期需修订」还是「需保留悬空引用以覆盖失败路径」。
